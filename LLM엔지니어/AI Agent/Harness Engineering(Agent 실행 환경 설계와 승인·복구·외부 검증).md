# 2026-09-01 Harness Engineering(Agent 실행 환경 설계와 승인·복구·외부 검증)

> 특강 「기술 톺아보기: Harness Engineering」을 듣고, 강의 자료를 그대로 옮기는 대신
> **내 언어로 재구성하고 직접 만든 예시·체크리스트를 덧붙여** 정리한 문서입니다.
> 수치와 사례는 원리를 설명하기 위한 예시이며 특정 제품의 공인 기준이 아닙니다.

## 오늘의 TIL 요약

**1강. 모델이 "말하는 것"과 시스템이 "실제로 바꾸는 것"의 경계**
- 지금까지 배운 딥러닝은 `입력 → 모델 추론 → 출력`이 전부였음. 여기서 한 걸음 더 나가면 **출력이 실제 세계를 바꾸는 순간**이 생기고, 그 순간부터는 모델 이야기가 아니라 **시스템 설계** 이야기가 됨
- ⭐ **오늘의 가장 중요한 한 줄**: 모델은 "Tool을 이렇게 호출하라"는 **형식(제안)**을 만들 뿐이고, 파일 수정·서버 재시작·결제 같은 **외부 상태 변경은 실행 프로그램이 Tool을 실제로 호출할 때** 일어남
  - 즉 **모델의 출력 자체는 외부 시스템의 행동이 아님**. 이 경계를 흐리면 "모델이 서버를 껐다"는 잘못된 문장이 나옴

  | 계층 | 무엇을 하는가 | 착각하기 쉬운 지점 |
  | --- | --- | --- |
  | 딥러닝 모델 | 학습된 매개변수로 입력을 처리해 예측/표현/생성을 만듦 | 출력 자체가 외부 시스템의 행동은 **아님** |
  | LLM | 입력 문맥을 바탕으로 텍스트나 정해진 형식의 응답을 생성 | Tool 호출 **형식**은 만들지만 직접 서버를 바꾸지는 **않음** |
  | Agent | 목표를 보고 Tool을 선택하고, 결과를 관찰하며 다음 행동을 정함 | 모델의 제안이 프로그램을 통해 **실제 행동으로 이어짐** |
  | Harness | Agent 주변에서 권한/승인/상태/검증/복구를 관리 | **모델을 다시 학습시키는 기법이 아니라 실행 환경을 설계하는 영역** |

- **Tool Calling의 최소 흐름 5단계** — 누가 무엇을 하는지 주어를 붙여서 외우기
  1. **프로그램**이 사용할 수 있는 Tool과 입력 형식(Schema)을 모델에게 알려줌
  2. **모델**이 사용할 Tool과 입력값을 제안함
  3. **프로그램**이 입력 형식을 확인함
  4. **프로그램**이 Tool을 실행함
  5. **프로그램**이 실행 결과를 모델에게 전달함
- ⛔ **이 5단계만으로는 자동으로 생기지 않는 것**: 사람 승인, 세밀한 권한 정책, 상태 저장, 외부 완료 검증, 중복 실행 방지, 복구
  - "Tool을 연결했으니 안전하겠지"가 아니라, **위 항목들은 하나하나 따로 설계해야 생기는 기능**
- Agent의 최소 반복 구조는 결국 이 Loop 하나

  ```
  사용자 목표 → 다음 행동 선택 → Tool 실행 → 결과 관찰 → (계속할 작업이 있는가?)
                    ↑                                              │ 예
                    └──────────────────────────────────────────────┘
                                                                   │ 아니오 → 최종 결과
  ```

  - ⭐ 이 도식에는 **검증·권한·승인·복구가 하나도 없음**. 그 빈칸을 채우는 것이 Harness

**2강. 통제 수준으로 본 3단계 (교육용 성숙도 구분)**
- 업계 표준 분류가 아니라 **"통제가 어디까지 설계되어 있는가"를 설명하기 위한 구분**. 간단한 Tool Loop도 최소한의 Harness로 볼 수 있어서 경계는 연속적임

  | 단계 | 추가되는 능력 | 운영 관점에서의 의미 |
  | --- | --- | --- |
  | 기본 모델 | 입력 문맥으로 출력을 생성 | 외부 상태 변경은 별도 실행 프로그램이 있어야 발생 |
  | Tool을 사용하는 Agent | Tool을 선택하고 결과를 관찰하며 다음 행동을 정함 | 최소 실행 Loop는 있지만 **권한/복구/검증 수준은 구현마다 크게 다름** |
  | 운영용 Harness를 갖춘 Agent | 정책, 승인, 상태, 외부 검증, 복구, 평가와 추적 | 위험을 제한하고 **성공/실패를 재현 가능하게 판단** |

- ⭐ **같은 모델이라도 문서·Tool·권한·완료 기준·복구 흐름에 따라 실제 성공률이 달라짐** → 성능을 올리는 지렛대가 모델 밖에도 있다는 뜻
- ⛔ 체크리스트를 충족했다는 사실만으로 실제 운영 배포가 안전하다고 판단할 수는 없음 (설계 검토 범위일 뿐 안전성 인증이 아님)

**3강. Prompt와 Tool만 연결하면 왜 부족한가 — 지연 장애 시나리오**
- 상황: Private LLM API가 평소 1초 안에 응답했는데 지금은 **약 4초**. Agent는 범위가 제한된 **지표/로그 조회 Tool**과 **서버 재시작 Tool**에 접근 가능. 재시작은 모든 수강생에게 영향을 주므로 **정책상 사람 승인 후에만** 실행되어야 함
- **통제가 없을 때 Agent가 저지를 수 있는 실수 9가지** — 성격별로 묶어서 보면 외우기 쉬움

  | 분류 | 구체적 실수 | 빠져 있는 통제 |
  | --- | --- | --- |
  | 근거 없음 | 지표/로그를 확인하기 전에 원인을 추측함 | 근거 수집 선행 규칙 |
  | 과도한 조회 | "읽기 작업"이라는 이유만으로 민감 로그를 과하게 조회함 | 조회 범위·민감도·Egress 제한 |
  | 입력 오류 | 잘못된 입력값으로 Tool을 호출함 | 입력 Schema 검증 |
  | 무한 반복 | 같은 실패를 제한 없이 반복함 | Retry Budget / Circuit Breaker |
  | 낡은 정보 | 오래된 Runbook·Memory를 현재 사실처럼 사용함 | 출처·최종 검토일·신뢰도 검증 |
  | 권한 위반 | 승인 없이 운영 서버를 재시작함 | 사람 승인 Gate |
  | 중복 실행 | 성공 여부가 불명확한데 같은 변경을 다시 실행함 | 멱등성·중복 실행 방지 |
  | 거짓 완료 | 실제로는 실패했는데 "정상화했습니다"라고 답함 | 외부 완료 검증 |
  | 추적 불가 | 실행 과정과 승인 근거가 남지 않아 사고를 재구성할 수 없음 | Trace / Audit Log |

- ⭐ **"모델이 더 똑똑해지면 다 해결되지 않나요?"** — 모델 능력 향상은 도움이 되지만, **권한 경계·입력 검증·승인·중복 실행 방지·완료 조건처럼 시스템이 강제해야 하는 문제를 모델 판단에만 맡길 수는 없음**
  - 면접에서 쓰기 좋은 대답: *"확률적으로 잘하는 것"과 "구조적으로 못 하게 막는 것"은 다른 층위의 보장이기 때문*

**4강. Agent Harness와 Harness Engineering**
- **Agent Harness** = 모델 주변에서 ① 목표와 Context를 제공하고 ② Tool 실행을 통제하고 ③ 상태를 저장하고 ④ 실제 결과를 검증하고 ⑤ 실패를 복구/추적하게 만드는 **실행 환경(Runtime)**
- 💡 자동차 비유: **모델은 엔진**에 가깝고, 목적지까지 안전하게 가려면 **운전대·브레이크·내비게이션·계기판·안전 규칙**이 필요함. Harness가 바로 그 실행/안전/관찰 장치
- ⭐ **Harness가 답해야 할 다섯 질문** — 이 표 하나가 오늘 내용의 뼈대

  | # | 질문 | 관련 설계 | 영문 설계 용어 |
  | --- | --- | --- | --- |
  | 1 | 무엇을 달성해야 하나요? | 목표, 제약조건, 완료 기준 | Goal, Constraints, Acceptance Criteria |
  | 2 | 무엇을 알아야 하나요? | 필요한 문서와 현재 정보 | Context, Documentation, Memory |
  | 3 | 무엇을 할 수 있고 누가 허용하나요? | 도구 입력 형식/권한/사람 승인 | Tool Schema, Authorization, Policy, Human Approval |
  | 4 | 실패하면 어떻게 이어가나요? | 진행 상태 저장/제한된 재시도/담당자 이관 | State, Checkpoint, Retry, Resume, Escalation |
  | 5 | 성공을 어떻게 증명하고 개선하나요? | 실제 결과 확인/기록/평가와 개선 | External Validator, Test, Eval, Trace, Feedback |

  - 한 번 정하고 끝내는 체크리스트가 아니라 **실행과 검증을 거치며 반복해서 갱신하는 설계 나침반**
- **Harness Engineering** = Agent와 주변 실행 환경을 **설계하고, 측정하고, 반복적으로 개선하는 활동**
  - 핵심 원리 3가지: **Agent-readable 환경**(Agent가 읽을 수 있는 형태로 정보를 놓기), **기계적 검사**(사람 눈이 아니라 코드가 판정), **Feedback Loop**(측정 → 개선 반복)
  - 쉽게 말해 → *Agent가 **허용된 범위에서** 행동하고, **실패 시 멈추거나 복구**하며, **실제 결과로 성공을 확인**하도록 실행 환경을 설계/개선하는 일*
- ⭐ **네 영역 구분** — 서로 겹치지만 던지는 질문이 다름

  | 관점 | 핵심 질문 | 한 단어 |
  | --- | --- | --- |
  | Prompt Engineering | 모델에게 작업을 어떻게 명확하게 지시할까? | **지시** |
  | Context Engineering | 현재 판단에 필요한 정보를 어떤 구조와 순서로 제공할까? | **정보** |
  | Harness Engineering | Agent가 어떻게 행동하고, 검증하고, 멈추고, 복구하며 개선될까? | **통제·검증·복구** |
  | LLMOps | 이 시스템을 어떻게 버전 관리하고 배포/모니터링/운영할까? | **운영** |

  - Harness Engineering의 특징은 Prompt와 Context를 넘어 **실행/통제/검증/복구/운영 Feedback Loop까지 함께** 본다는 점

**5강. 장애 대응 흐름으로 보는 역할 분담**
- 목표 정의: *지연 증가 원인을 근거와 함께 설명하고, **승인 없이 운영 시스템을 바꾸지 않으며**, 조치 후 응답 시간이 다시 기준 안에 들어왔는지 **외부 지표로 확인**한다*
- **네 역할이 이어지는 운영 흐름** — Agent 혼자가 아니라 네 주체가 릴레이함

  | 단계 | Agent | Harness | 사람 승인자 | 외부 시스템 |
  | --- | --- | --- | --- | --- |
  | 감지·진단 | 조치 계획 수립 | **제한된 조회**로 근거 수집 | – | 지연 경보 제공 |
  | 계획·승인 | 계획 제안 | **정책 판단** → 승인 필요 여부 결정 | **승인 / 거절** | – |
  | 통제 실행 | – | **권한·대상 재검사**, **중복 방지 실행** | – | – |
  | 외부 검증 | – | 완료 / 이관 판정 | – | **외부 증거 제공** |

  - ⭐ **핵심 경계**: Agent는 **계획을 제안**하지만, 조회 범위·승인·재검사·중복 방지·완료 판정은 **Harness와 외부 증거가 책임**짐
  - ⛔ 승인 후에도 **권한과 대상이 그대로인지 다시 검사**함. 승인 시점과 실행 시점 사이에 상태가 바뀔 수 있기 때문
- ⭐⭐ **Tool 실행과 작업 완료는 같은 사건이 아님**
  - `Tool 호출 기록` = **시도했다는 증거** (ATTEMPTED ≠ SUCCEEDED)
  - `외부 지표 통과` = **완료 증거** (관찰 시간 동안 유지되어야 인정)
- **완료 기준 예시** — 숫자 자체가 아니라 **"외부에서 관찰할 완료 기준을 미리 정의한다"는 원리**가 배울 점

  ```
  변경 후 10분 동안, 매 1분마다 확인해서 아래가 "계속" 만족되어야 완료
    ├─ p95 응답 시간 ≤ 1.2초        (전체 요청의 95%가 1.2초 안에 응답)
    ├─ 서버 오류 응답 비율 ≤ 1%
    ├─ Health Check 3회 연속 통과
    └─ 신규 GPU 메모리 부족 오류 / 서버 Process 재시작 0건

  하나라도 실패 → 완료 선언 금지 → Rollback | 재계획 | 사람 이관 중 택 1
  ```

  - 실제 프로젝트에서는 해당 서비스의 **SLO와 위험 수준**에 맞게 기준을 정함
- **같은 장애, 다른 결과**

  | 구분 | Prompt/Tool만 연결 | 운영용 Harness를 갖춘 Agent |
  | --- | --- | --- |
  | 첫 행동 | 원인을 추측하거나 즉시 재시작할 수 있음 | **범위를 제한한 지표/로그 조회부터** 시작 |
  | 변경 | 모델 판단에 따라 바로 실행할 수 있음 | **정책 검사 + 구체적인 사람 승인**을 통과해야 함 |
  | 복구 | 실패 시 같은 행동을 반복할 수 있음 | **횟수/시간/비용 한도와 중복 방지 기준**이 있음 |
  | 완료 | Agent의 자기보고로 끝날 수 있음 | **외부 지표와 실제 상태**로 판정 |

**6강. 직접 해보기 — Harness 미니 캔버스**
- 새로운 업무에 Agent를 붙일 때, 구현 기술이나 제품명을 적기 전에 **행동 경계부터 다섯 칸으로 설계**하는 연습

  | 항목 | 스스로에게 던질 질문 |
  | --- | --- |
  | 목표 | Agent가 무엇을 달성해야 하나요? |
  | 자동 허용 | 어떤 조건을 충족한 행동을 자동 실행해도 되나요? |
  | 사람 승인 | 어떤 행동은 실행 전에 누구에게 물어야 하나요? |
  | 완료 증거 | 무엇을 확인해야 실제 성공이라고 판단할 수 있나요? |
  | 실패 처리 | 언제 멈추고, 되돌리고, 누구에게 넘기나요? |

- ⭐ **잘 작성했는지 확인하는 기준 2가지**
  1. **자동 허용과 사람 승인이 분리**되어 있는가
  2. **완료 증거가 Agent의 말이 아니라 외부 상태**인가
  - 추가로 실패 시 **중단 / 되돌리기 / 담당자 이관** 조건까지 적혀 있으면 충분
- 💡 **직접 채워본 예시 — "회의록 자동 정리 Agent"** (배운 원리를 다른 업무로 옮겨 연습)

  | 항목 | 작성 내용 |
  | --- | --- |
  | 목표 | 회의 녹취에서 결정사항·액션아이템을 추출해 사내 위키에 초안 페이지를 만든다 |
  | 자동 허용 | 지정된 폴더의 녹취 파일 **읽기**, 위키 **초안 공간에 새 페이지 생성** |
  | 사람 승인 | **기존 페이지 덮어쓰기**, **외부 참석자에게 메일 발송**, **공개 범위 변경** |
  | 완료 증거 | 페이지가 목표 경로에 존재 + 필수 섹션(결정/액션/담당자) Schema 검사 통과 + Audit Log 기록 |
  | 실패 처리 | 추출 신뢰도 미달 3회 → 중단하고 초안에 `검토 필요` 표시 후 회의 주최자에게 이관 |

**7강. 이해도 확인 — 반드시 구분해야 할 원칙**
1. **모델이 행동을 제안하는 것**과 **프로그램이 외부 시스템을 실제로 바꾸는 것**은 다름
2. **Tool을 연결하는 것만으로 권한/검증/복구가 생기지는 않음**
3. 위험한 행동은 **구체적인 대상과 입력값에 결합된** 사람 승인이 필요함
4. 성공은 **Agent의 자기보고가 아니라 별도 검사와 실제 외부 상태**로 확인함
- ⛔ **추가로 헷갈리기 쉬운 두 가지**
  - **읽기 전용 작업도 위험할 수 있음** — 민감정보를 지나치게 읽거나, 외부로 내보내거나, 큰 비용을 유발하는 경우
  - **Checkpoint는 만능 되돌리기가 아님** — 작업 **진행 상태**를 저장할 뿐, **이미 실행한 서버 재시작/결제/발송을 되돌리지는 못함**

**8강. (선택 심화) 실제로 구현한다면 어디를 설계해야 하는가**
- AI Agent / MCP / LLMOps를 배운 뒤 다시 볼 후속 심화 영역. 지금은 세부 구현을 외우기보다 **"Agent가 실제 행동을 하면 승인·중복 실행 방지·장애 복구·외부 검증을 별도로 설계해야 한다"는 문제의식**만 잡으면 충분
- **설계가 흘러가는 순서**

  ```
  A. 설계 경계        →  B. 실행 안전   →  C. 다층 방어  →  D. 품질 평가       →  E. 단계적 도입
  목표/Context/권한/     승인/멱등성/      실패 유형별      Eval/Chaos/          Read-only →
  상태/증거              Reconcile         안전장치        Release Gate         Staging → Production
  ```

- **A. Context와 문서** — Agent가 실행 중 접근할 수 없는 지식은 활용할 수 없음
  - 문서에는 **소유자, 마지막 검토일, 적용 대상, Version**을 기록 (낡은 Runbook을 현재 사실처럼 쓰는 사고 방지)
  - Memory에 쓰기 전에 **출처와 신뢰도를 검증**
  - ⭐ **Secret 원문은 Context/Memory/Checkpoint/Trace에 넣지 않고 불투명한 Handle로 참조**
- **A. Tool 권한과 승인** — 모델이 Tool 호출을 제안했다고 바로 실행하지 않음
  1. Tool **Allowlist**와 입력/출력 **Schema** 검증
  2. **사용자 / Agent / Tool / 대상 Resource / Tenant / 목적**을 함께 인가
  3. Mutation 여부와 **별도로** 데이터 민감도, Egress, 비용, 범위를 평가
  4. **자동 허용 / 사람 승인 / 기본 차단** 중 하나를 선택
  5. **승인 대기 중에는 Tool을 실행하지 않음**
  - **읽기 작업 자동 허용 조건** (모두 충족된 저위험 조회만): 신뢰된 Server, 사용자/Tenant 최소 권한, 조회 대상·기간·필드 제한, PII/Secret Redaction, Rate/Cost 제한, 외부 전송 금지
  - ⭐ **승인 요청에 담아야 할 정보** — "재시작해도 될까요?"가 아니라 **대상과 입력값이 확정된 승인**이어야 함
    - 요청 사용자, 승인자와 Role, Operation ID, Tool Server/Tool/Target/Tenant, 정규화된 Payload, 예상 영향, 데이터 공개 대상, Rollback 방법, Policy Version, **승인 시점의 대상 상태 Hash**, 만료 시간, 일회 사용 여부, Action digest
    - ⛔ **승인된 입력값·대상 상태·정책이 바뀌면 기존 승인을 재사용하지 않고 다시 승인받음**
  - **동시 실행 방지**: 승인 검증만으로는 부족함. 실행 직전에 승인을 **특정 Operation이 원자적으로 Claim**하고, `WAITING_APPROVAL → EXECUTING` 상태 전환과 실행 Intent 기록을 **하나의 작업으로** 처리
- **A. State / Checkpoint / Resume**
  - ⭐ **Checkpoint는 실행 프로세스 자체나 외부 세계의 Snapshot이 아니라 Workflow State의 저장본** → 이미 실행한 재시작/결제/발송을 자동으로 되돌리지 않음
  - State에 담을 것: `task_id`, 현재 상태, 수집 근거, Pending Action, Approval Reference, Action Ledger, Retry Count, Validation Result
  - `state_schema`, graph/code, prompt, model, tool schema, policy Version을 **함께 기록**해야 나중에 재현 가능
  - 암호화, RBAC, TTL, 무결성 검증을 적용하고, Resume 시 **소유권·Credential·승인·Tool Schema·정책·외부 상태를 다시 검사**
  - ⛔ **LangGraph의 `interrupt()` 후 Resume은 정확히 그 코드 줄에서 이어지는 것이 아니라 해당 Node를 처음부터 다시 실행**함
    - → Side Effect는 Interrupt **이후 별도 Node로 분리**하고, 외부 변경은 Idempotency Key / 실행 Intent / Outcome Ledger / Atomic Claim / 중복 감지 / Reconcile로 보호
- **A. 외부 Validator / Trace / Audit** — Agent의 자기보고와 실제 Outcome을 분리
  - 파일, 데이터베이스, Health Check, Metric, Test처럼 **모델 밖에서 읽을 수 있는 상태**로 성공을 판정
  - **Operational Trace**(단계, Version, Tool, 지연, 오류와 재시도 원인)와 **Security Audit**(누가, 어떤 정책 결정과 승인으로, 어떤 대상에, 무엇을 실행했는지)을 **Append-only 또는 Tamper-evident**로 분리 기록
  - ⛔ 별도 Worker의 Outbox 전달은 일반적으로 **at-least-once**이므로 같은 Event가 다시 전달될 수 있음 → **Transactional Outbox 자체를 end-to-end exactly-once 보장으로 해석하면 안 됨**
  - Prompt/Tool 입력·결과 원문은 기본 수집으로 간주하지 않고 Redaction/DLP 적용 후 필요한 범위에서만 Opt-in
- **B. 안전한 실행 Loop 상태 머신** — 승인/복구/중복 실행을 한 그림으로

  ```
  PLAN → VALIDATE ─┬─ Schema/Policy 실패 ──────────→ REPLAN ──→ PLAN
                   ├─ 승인 필요 ──→ WAITING_APPROVAL ─┬─ 거절/만료/대상 변경 → REPLAN
                   │                                  └─ 승인+권한 재검사 통과 → CLAIM
                   └─ 사전 정책으로 자동 허용 ──────────────────────────────→ CLAIM

  CLAIM ─┬─ 원자적 Claim 성공 ─────→ EXECUTE ─┬─ 결과 확정 ──→ VERIFY
         └─ 이미 실행 중/결과 불명확 → RECONCILE └─ 결과 불명확 → RECONCILE

  RECONCILE ─┬─ 미실행 확인 → 안전한 재시도 ──→ EXECUTE
             ├─ 기존 성공/실패 결과 확인 ─────→ VERIFY
             └─ 결과 확인 불가 ───────────────→ ESCALATE

  VERIFY ─┬─ 외부 완료 조건 통과 ──→ DONE
          ├─ 복구 가능한 실패 ─────→ REPLAN
          └─ 한도 초과/고위험 실패 → ESCALATE
  ```

  - ⭐ 읽는 법: **승인이 필요한 행동은 `WAITING_APPROVAL`에서 실행을 종료**함. 승인 후에도 권한과 대상을 재검사하고, 승인 Claim·상태 전환·실행 Intent 기록을 원자적으로 처리함. **이미 실행 중이거나 결과가 불명확하면 Tool을 다시 호출하지 않고 먼저 결과를 대조(RECONCILE)함**
  - ⛔ Tool 호출이 명시적으로 실패한 경우에도 이를 성공으로 기록하지 않고, 실패 Outcome을 저장한 뒤 외부 Validator와 복구 정책으로 다음 상태를 결정
- **B. Idempotency Key가 보장하는 범위** — 오해하기 쉬운 부분
  - ⭐ 목표는 **정해진 범위 안에서 같은 논리 Operation의 반복 요청이 추가 효과를 만들지 않게** 하는 것
  - ⛔ 네트워크·데이터베이스·외부 시스템을 포함한 **물리적 실행 전체가 exactly-once였음을 자동으로 증명하지는 않음**

  | 확인 항목 | 반드시 정할 Contract |
  | --- | --- |
  | Key Scope | Tenant, Tool Server, Tool, Target, Operation ID 중 어디까지가 같은 Key의 중복 범위인지 |
  | Input Binding | 정규화된 Payload와 Action digest를 Key에 결합 → **같은 Key에 다른 입력이 오면 재사용하지 않고 거절** |
  | Concurrency | 동시에 들어온 같은 요청 중 하나만 실행 주체가 되도록 Unique Constraint / Atomic Claim |
  | Result Lookup | 같은 Key로 `in progress`, `succeeded`, `failed`, `unknown` 상태와 저장된 Outcome을 조회 가능 |
  | Retention | Key와 Outcome을 Retry/Reconcile 가능 기간보다 오래 보존하고, 만료 후 정책을 명시 |

  - 상태에 따라 안전성이 달라지는 Mutation은 승인 여부와 관계없이 **실행 전에 외부 상태를 읽어 `precondition_digest`를 계산하고 Action에 결합**함. Claim 시점의 현재 상태와 다시 비교해 값이 바뀌었으면 실행하지 않고 재계획
  - ⭐ **Fail-closed 원칙**: 권한/승인/입력 결합/기준 상태/결과를 **확인할 수 없으면 허용하거나 완료로 선언하지 않음**
- **C. 대표 실패 유형과 다층 안전장치**

  | 실패 유형 | 주요 안전장치 |
  | --- | --- |
  | Goal Hijacking / Prompt Injection | Instruction과 Untrusted Data의 **구조적 분리**, Schema 기반 추출, Provenance, 입출력 검증, Tool Policy Gate, Egress 제한, 적대적 Eval |
  | Tool Misuse / 과도한 권한 | 최소 권한, Allowlist, Resource·Tenant 단위 인가, 입력값 검증, 고위험 승인, Sandbox |
  | Identity / Credential 오용 | 사용자 위임 Identity와 **Agent Identity 분리**, 짧은 수명·최소 Scope Credential, 매 호출 재인가, **Token Passthrough 금지** |
  | Supply Chain / Code Execution | Tool·MCP Server 출처 확인, **Version Pinning**, 서명/검토, 파일·프로세스·네트워크 Sandbox |
  | Memory Poisoning | 쓰기 권한 분리, 출처·신뢰도 기록, 승인 또는 검증 후 장기 Memory 반영, TTL |
  | Cascading Failure / 무한 Loop | 최대 Step·시간·비용, **Retry Budget**, Circuit Breaker, 중복 감지, 사람 이관 |
  | Approval Fatigue | 영향과 변경 내용을 **짧고 구체적으로** 표시, 일회성 승인, 반복 거절 존중, **고위험 행동에 승인 집중** |

  - ⛔ **외부 문서/로그/Tool Result를 "데이터"라고 표시하는 것만으로 Prompt Injection이 무력화되지 않음** → 완전한 단일 방어를 기대하지 말고 구조 분리 + 검증 + 최소 권한 + 정책/승인 + Egress 제한 + 적대적 평가를 **함께** 적용
  - 💡 Approval Fatigue가 안전장치 목록에 들어 있는 게 인상적이었음. **사람이 지쳐서 다 승인 눌러버리면 승인 Gate는 없는 것과 같다**는 뜻 — 보안은 기술만이 아니라 사람의 인지 부하까지 설계 대상
- **C. MCP를 사용할 때 추가로 확인할 것**
  - ⭐ **상태의 경계**: MCP `2026-07-28` Core는 **프로토콜 계층에서 Stateless**임. 이는 애플리케이션이나 Tool이 상태를 가질 수 없다는 뜻이 **아님**. 여러 호출에 걸친 상태가 필요하면 Tool이 **명시적 Handle**을 반환하고 이후 호출이 그 Handle을 입력값으로 전달하도록 설계
    - ⛔ 인증된 Server는 **Handle을 권한 자체로 간주하지 않고 매 호출마다 요청자의 접근 권한을 다시 확인**함
  - **MCP Client/Host의 책임**: 최소 Scope만 요청, 대상 Server를 가리키는 Resource Indicator 사용, Authorization 응답의 Issuer 검증, **MCP Server용으로 발급된 Token만 해당 Server에 전송**, `ToolAnnotations.readOnlyHint`를 **신뢰 경계로 사용하지 않기**
  - **보호된 MCP Server의 책임**: OAuth Resource Server로서 Token 유효기간·Issuer·Audience·대상 Resource·Scope 검증, Tool 호출마다 Resource/Tenant 수준 접근 제어, 모든 입력 검증과 Rate Limit, 출력 정제, **Access Token을 Downstream API에 그대로 전달하지 않기**
  - **Transport 차이**: 위 HTTP Authorization 흐름은 **원격 HTTP Transport**용. **STDIO Transport는 이 흐름을 쓰지 않으므로** OS 권한, 환경변수, Credential 주입, 프로세스·파일·네트워크 Sandbox를 **별도로** 설계해야 함
- **D. 품질 평가 — Eval / Chaos Test / Release Gate**
  - Eval은 지표 이름을 적는 것으로 끝나지 않고, 각 Eval마다 다음을 정의: ① Objective와 실패 위험 ② Dataset Version과 실제 운영 분포 ③ 학습·개발용과 **Held-out Regression Set의 분리** ④ Case별 Trial 수와 **깨끗하고 격리된 초기 환경** ⑤ Grader/Formula/Threshold와 신뢰구간 ⑥ 사람 Label과 Model Grader의 정기 교정 ⑦ **실패 시 Release를 차단하는 규칙**

  | 지표 | 던지는 질문 |
  | --- | --- |
  | Task Success Rate | 실제 외부 완료 조건을 충족했나요? |
  | Policy Violation Rate | 승인 우회, 권한 밖 행동, Secret 유출이 있었나요? |
  | Recovery Success Rate | Timeout/Crash 후 **중복 Side Effect 없이** 복구했나요? |
  | Tool Decision Quality | 여러 유효한 경로를 허용하면서 필수/금지 Tool 행동을 지켰나요? |
  | Latency / Cost / Human Intervention | 정확성과 안전성을 유지하면서 운영 한도를 지켰나요? |

  - ⭐ **`pass@k` vs `pass^k`** — 헷갈리기 쉬운 한 쌍

    | 지표 | 정의 | 공식(독립·동일 조건 가정) | 언제 쓰나 |
    | --- | --- | --- | --- |
    | `pass@k` | 한 Task를 독립적으로 k번 시도했을 때 **한 번 이상** 성공할 확률 | `1 - (1 - p_i)^k` | 탐색 가능한 여러 시도 중 **하나의 성공**이 중요할 때 |
    | `pass^k` | 같은 Task의 독립적인 k번 Trial이 **모두** 성공할 확률 | `p_i^k` | **반복 일관성과 신뢰성**이 중요한 운영 작업 |

    - ⛔ Suite 계산 순서 주의: **각 Task의 값을 먼저 계산한 뒤 Task 전체에서 평균**함. 전체 Trial을 합쳐 만든 하나의 평균 성공률에 공식을 한 번 적용하는 것과 **다름**
    - ⛔ 공유 Cache, 남은 파일, 자원 고갈, 공통 장애로 Trial이 서로 영향을 받으면 **독립성 가정이 깨짐** → 매 Trial을 깨끗하고 격리된 환경에서 실행하고 **신뢰구간과 표본 수를 함께 보고**
    - `k=1`에서는 `pass@k`와 `pass^k`가 모두 Trial별 성공률과 같음
  - **별도 Chaos Test가 필요한 경계** (평상시 Eval로는 잡히지 않는 것들)
    - 두 Worker가 같은 승인을 **동시에** Resume / 승인 Claim 후 **Tool 호출 전** 중단 / Tool **Side Effect 후 응답 전** Timeout / Tool **응답 후 Outcome 저장 전** 중단 / 같은 Message 중복 전달 / **승인 후 Target·Payload·Policy 변경**
    - ⭐ 모든 Case에서 검증할 목표: **승인 Claim 1회, 설계한 논리 Operation 범위에서 외부 Side Effect 최대 1회, 결과 불명 시 재실행 대신 Reconcile**
  - **예시 Release Gate**: Task Success의 95% 신뢰구간 하한이 업무 목표 이상 / 승인 우회·권한 밖 변경·Canary Secret 유출 관측 0건 / Crash·Timeout Chaos Trial에서 중복 Side Effect 0건 / 승인 거절·만료·입력값 변경 Case에서 Tool 실행 0건 / Prompt Injection Case에서 허용되지 않은 Tool Call·외부 Egress·민감정보 공개 0건
- **E. Read-only MVP에서 Production까지 10단계** — 실제 구축 순서
  1. 하나의 **좁고 측정 가능한** 업무를 선택
  2. **외부에서 판정 가능한** 완료 기준과 금지 조건을 정의
  3. State, Action Ledger와 Version 필드를 설계
  4. Agent가 읽을 **문서 지도**와 Context 정책을 마련
  5. Tool Registry에 Schema, Timeout, Retry, 위험도, 검증 방식과 **Idempotency Contract**를 기록
  6. **자동 허용 / 사람 승인 / 기본 차단** Policy를 구현
  7. Checkpoint, **논리적 Idempotency**, Reconcile, Resume 흐름을 구현
  8. **모델 밖의** 외부 Validator를 구현
  9. 정상 / 오류 / 공격 / 승인 거절 / Crash Case가 포함된 Eval과 Trace를 구축
  10. **Read-only → Staging → 승인 기반 Production** 순으로, 수치화된 Exit Gate를 통과할 때만 권한을 확대
  - ⭐ **고위험 작업의 승인 원칙은 성숙도가 높아져도 자동으로 사라지지 않음** (10단계를 다 밟았다고 승인 Gate를 없애는 게 아님)

**9강. 공식 자료를 읽을 때 확인할 순서**
1. 문서가 설명하는 대상이 **모델 / Agent Runtime / Protocol / Eval Harness** 중 무엇인지 확인
2. **개념 설명**과 **특정 제품·Framework의 기능**을 구분
3. ⭐ **"지원한다"는 표현이 상태 저장, 외부 Side Effect 복구, 보안 보장 중 무엇을 뜻하는지** 확인
4. Version과 게시일을 확인하고, `draft`·legacy·moved 표시가 있는 링크는 고정 Version 또는 현재 문서로 교체
5. 예제 코드는 **승인 거절, Crash Window, 중복 실행, 민감정보 기록 같은 실패 경로까지** 검토
- ⛔ Agent 기술과 Framework는 빠르게 변함 → MCP는 실습 시점의 최신 Stable Version을 다시 확인하고, OpenTelemetry GenAI Convention은 사용하는 Version 또는 Commit을 고정

**오늘 배운 것 한눈에 정리**
- ⭐ **모델의 출력은 "제안"이고, 외부 상태를 실제로 바꾸는 것은 "실행 프로그램"** — 이 경계가 오늘 내용 전체의 출발점
- Tool Calling의 최소 5단계만으로는 **승인·권한 정책·상태 저장·외부 완료 검증·중복 방지·복구가 자동으로 생기지 않음**
- **Agent Harness**는 모델 주변에서 목표/Context 제공, Tool 실행 통제, 상태 저장, 결과 검증, 실패 복구를 담당하는 **실행 환경(Runtime)**이고 **모델 재학습 기법이 아님**
- Harness는 다섯 질문(**목표 / 정보 / 권한·승인 / 실패 처리 / 완료 증명**)을 반복해서 갱신하며 설계
- **Prompt = 지시, Context = 판단에 필요한 정보, Harness = 행동의 통제·검증·복구, LLMOps = 운영**
- ⭐ **Tool 호출 기록은 시도 증거일 뿐 완료 증거가 아님** — 완료는 p95 응답 시간, 오류율, Health Check 같은 **독립된 외부 기준이 관찰 시간 동안 통과**해야 인정
- 위험한 행동의 승인은 **구체적 대상과 입력값에 결합**되어야 하고, 승인 후에도 **권한·대상을 재검사**하며, 대상·입력·정책이 바뀌면 **재승인**
- **Checkpoint는 Workflow State 저장본이지 외부 세계 Snapshot이 아님** — 이미 실행한 재시작/결제/발송은 되돌리지 못함
- 결과가 불명확할 때의 정답은 **재실행이 아니라 Reconcile**, 확인조차 불가능하면 **Fail-closed**
- **읽기 전용 작업도 안전하지 않음** — 민감정보 과다 조회, 외부 전송, 큰 비용 유발은 그 자체로 위험

**데일리 퀴즈 정리**
1. Private LLM API가 느려졌을 때 **가장 적절한 첫 행동**은? → **허용 범위 안에서 지표와 로그를 수집하고 완료 기준을 확인한다**
   - ⛔ 오답 ① *즉시 운영 서버 재시작* — 영향이 큰 변경이므로 **원인·영향·Rollback을 제시하고 승인을 받아야 함**
   - ⛔ 오답 ② *모델에게 원인에 대한 자신감을 다시 묻기* — 자기보고는 외부 근거가 아님
   - ⛔ 오답 ③ *Prompt를 더 길게 바꾸기* — 지시 문제가 아니라 **근거 수집 순서** 문제
   - 승인 없이 즉시 재시작할 때의 위험: 근거 없이 잘못된 원인을 조치해 **장애를 악화**시킬 수 있음 / 승인 없이 **수강생 전체 서비스를 중단**시킬 수 있음 / 결과가 불명확할 때 **같은 재시작을 반복**할 수 있음
2. **"작업 완료"의 가장 강한 증거**는? → **상태 확인과 지표가 정해진 시간 동안 기준을 만족하는 것**
   - ⛔ *재시작 Tool 호출 기록이 있다* — **시도했다는 증거일 뿐 성공 증거가 아님**
   - ⛔ *Agent가 "정상화했습니다"라고 답했다 / 원인을 길게 설명했다* — 자기보고와 설명 길이는 완료와 무관
   - ⭐ 완료는 **Agent와 분리된 검사와 실제 시스템 상태**로 확인해야 함
3. 다음은 각각 어느 단계인가?
   - *입력을 바탕으로 장애 원인에 대한 설명을 생성한다* → **기본 모델**
   - *지표 조회 Tool을 사용하고, 결과를 본 뒤 로그 검색 여부를 결정한다* → **Tool을 사용하는 Agent**
   - *운영 서버 재시작 전에 승인을 요구하고, 실행 후 외부 상태로 완료를 확인한다* → **운영용 Harness를 갖춘 Agent**
   - 정리: 모델은 **출력을 생성**하고, Agent는 **Tool을 사용하며 작업을 이어가고**, Harness는 **권한/승인/검증/복구의 실행 경계를 제공**함
4. Agent가 운영 서버 재시작을 제안했는데 **대상 서버 입력값이 잘못되었고 승인 여부도 확인되지 않는다면** Harness는? → **실행을 막고 입력값을 바로잡은 뒤, 정확한 대상과 영향에 대해 승인을 요청한다**
   - ⛔ *가장 비슷한 서버를 추측하여 실행* / *승인은 나중에 확인하고 먼저 실행* / *오류를 기록했으니 완료 처리* 모두 오답
   - ⭐ **입력값이나 승인 상태를 확인할 수 없으면 실행하지 않는다(Fail-closed)**. 승인은 **대상과 입력값이 확정된 행동**에 대해 구체적으로 받아야 함
   - **"왜 이것이 모델 재학습이 아니라 Harness Engineering인가?"** → 모델의 가중치나 출력 방식을 다시 학습시키는 것이 아니라, **Agent가 행동할 권한·승인 절차와 외부 완료 확인을 실행 환경에 설계했기 때문**
5. **기존 보고서 파일을 덮어쓰는 Agent**를 만든다면 자동 허용 / 승인 필요 / 완료 증거는?
   - **자동 허용**: 허용된 폴더 안에서 기존 파일의 **이름/크기/수정 시각만 조회**
   - **승인 필요**: 덮어쓰기 전에 **대상 경로, 변경 요약, 백업 위치를 보여주고 일회성 승인**을 받음
   - **완료 증거**: 파일이 **목표 경로에 존재**하고, **Schema 또는 문서 검사가 통과**하며, **백업과 Audit Log가 남았는지** 확인
   - ⭐ 이것이 Harness Engineering인 이유: 모델의 답변만 바꾸는 것이 아니라 **Agent가 행동할 권한, 승인 절차, 외부 완료 증거를 설계**했기 때문

**면접에서 물어보면 이렇게 답하기**
- *"Agent에 Tool만 붙이면 되는 것 아닌가요?"* → Tool 연결은 **행동할 수단**을 준 것이고, **행동해도 되는 범위(권한)·행동하기 전 확인(승인)·행동 후 판정(외부 검증)·실패했을 때의 처리(복구)** 는 별도 설계가 필요합니다. 수단과 통제는 다른 층위입니다.
- *"Agent가 작업에 성공했다는 걸 어떻게 아나요?"* → Agent의 자기보고는 증거로 쓰지 않고, **모델 밖에서 읽을 수 있는 상태**(파일 존재 여부, DB 레코드, Health Check, Metric)가 **정해진 관찰 시간 동안 기준을 만족**하는지로 판정합니다. Tool 호출 로그는 시도 증거일 뿐입니다.
- *"실패하면 재시도하면 되지 않나요?"* → 결과가 불명확한 상태에서의 재시도는 **중복 Side Effect**를 만듭니다. 먼저 **Reconcile**로 실제 실행 여부를 대조하고, 미실행이 확인될 때만 안전하게 재시도하며, 확인이 불가능하면 **Fail-closed로 멈추고 사람에게 이관**합니다.
- *"LLM 성능이 좋아지면 해결되지 않나요?"* → 모델 능력은 **확률적 개선**이고, 권한 경계·승인·중복 실행 방지·완료 조건은 **구조적 보장**이 필요한 영역입니다. 전자가 후자를 대체하지 못합니다.

**한 줄 정리**: 딥러닝에서 배운 `입력 → 추론 → 출력`의 다음 단계는 그 출력이 실제 세계를 바꾸는 지점인데 — **모델은 Tool 호출 "형식"을 제안할 뿐이고 외부 상태를 실제로 바꾸는 것은 실행 프로그램**이므로, Prompt와 Tool을 연결하는 최소 흐름만으로는 승인·권한·상태 저장·중복 실행 방지·외부 완료 검증·복구가 생기지 않아서 **Agent Harness라는 실행 환경**이 목표·Context·권한·실패 처리·완료 증명이라는 **다섯 질문**에 답하도록 설계되어야 하고, 그 핵심은 **위험한 행동은 대상과 입력값이 확정된 사람 승인 뒤에 실행하되 승인 후에도 권한·대상을 재검사하고, Tool 호출 기록은 시도 증거일 뿐이므로 완료는 p95 응답 시간·오류율·Health Check 같은 독립된 외부 기준이 관찰 시간 동안 통과해야 인정하며, 결과가 불명확하면 재실행 대신 Reconcile하고 확인조차 불가능하면 Fail-closed로 멈추는 것** — 즉 Harness Engineering의 목적은 Agent가 사람 없이 많은 일을 하게 만드는 것이 아니라 **허용된 범위에서 행동하고, 위험하면 멈춰 승인받고, 실패해도 중복 피해 없이 복구하며, 실제 결과로 성공을 증명할 수 있게** 만드는 것이다.
