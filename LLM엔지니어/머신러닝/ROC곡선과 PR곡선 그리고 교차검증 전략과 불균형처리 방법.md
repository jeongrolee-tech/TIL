# TIL | ROC-AUC·PR곡선, 불균형 처리, 교차검증 전략

**2026-08-14**

안전 필터 Accuracy가 98%인데 위험 답변을 하나도 못 막았다면, 그 숫자는 의미가 없다. 오늘은 **불균형 데이터에서 무엇을 평가하고(4장 1강), 어떻게 나눠서 검증할지(4장 2강)**를 다뤘다.

## 1. Accuracy의 함정과 혼동행렬

불균형 데이터에서는 모든 답변을 "정상"이라 예측해도 Accuracy가 98%가 나올 수 있다. 클래스 비율이 크게 치우치지 않고 FP·FN의 비용이 비슷할 때는 Accuracy가 유용하지만, **양성률과 오류의 종류를 확인하지 않은 채 Accuracy 하나로 모델을 승인하는 것**이 문제다.

혼동행렬은 threshold 하나를 정했을 때 나오는 TP·FP·FN·TN을 표로 정리한 것이다.

* **TP**: 실제 양성을 양성으로 맞춤
* **FP**: 실제 음성을 양성으로 잘못 판단 (거짓 경보)
* **FN**: 실제 양성을 음성으로 놓침
* **TN**: 실제 음성을 음성으로 맞춤

여기서 계산되는 지표:

* **Precision** = TP / (TP+FP) — 양성이라 예측한 것 중 실제 양성 비율
* **Recall** = TP / (TP+FN) — 실제 양성 중 찾아낸 비율
* **F1** = Precision과 Recall의 조화평균

> "시험을 보고 몇 문제를 맞고, 어떤 문제를 틀렸는지 종류별로 세어 놓은 성적표가 혼동행렬이다."

---

## 2. ROC-AUC와 AP — 같은 모델, 다른 질문

**ROC 곡선**은 "양성과 음성을 얼마나 잘 구분하는가?"를 묻는다. 세로축은 TPR(Recall), 가로축은 FPR(실제 음성을 양성으로 오판한 비율)이다.

문제는 **불균형이 심할 때 ROC가 착시를 만든다는 점**이다. 양성 10개, 음성 10,000개인 경우 FP가 10 → 20개로 두 배 늘어도 FPR은 0.001 → 0.002로 거의 안 변한다. TN(분모)이 워낙 크기 때문이다.

> "사탕이 990개, 돌멩이가 10개인 상자에서는 돌멩이를 몇 개 잘못 골라도 사탕이 많아서 성적이 좋아 보일 수 있다."

그래서 희소 양성 문제에서는 **PR 곡선(AP)**을 함께 봐야 한다. PR 곡선은 x축 Recall, y축 Precision으로, 양성을 많이 찾으려 threshold를 낮출수록 Precision이 떨어지는 관계를 보여준다. AP는 이 곡선의 면적을 요약한 하나의 숫자다.

| | 곡선 | 요약 지표 | 질문 |
|---|---|---|---|
| 전체 구분력 | ROC 곡선 | ROC-AUC | 양성/음성을 얼마나 잘 가르는가 |
| 소수 클래스 품질 | PR 곡선 | AP | 양성 예측이 얼마나 믿을 만한가 |

**주의**: `average_precision_score`의 AP(Recall 증가분으로 Precision을 가중합)와 `auc(recall, precision)`의 사다리꼴 면적은 계산 방식이 달라 값이 다를 수 있다. → AP로 통일해서 사용.

## 3. Threshold — 모델의 일부가 아니라 운영 정책

분류 모델은 점수(확률)만 계산하고, 통과/차단을 가르는 기준은 **threshold**다. 같은 점수 0.8도 threshold=0.5면 양성, threshold=0.9면 음성이 된다. threshold를 낮추면 Recall↑·Precision↓(FN 감소, FP 증가), 높이면 반대다.

기본값 0.5는 라이브러리 기본값일 뿐 서비스에 맞는 값이 아니다. 놓치면 위험한 문제(암 진단)는 threshold를 낮추고, 오탐이 더 문제인 경우(스팸)는 높인다. 예: `Cost = FP×1 + FN×5` 같은 비용 함수를 만들어 validation에서 비용이 가장 작은 threshold를 고른다.

**봉인 test 원칙**: train으로 학습 → validation에서 모델·threshold 선택 → 선택을 모두 고정한 뒤 test를 **한 번만** 평가. test를 보고 threshold를 다시 바꾸면 그 test는 더 이상 최종 평가가 아니다.

## 4. 불균형 처리 3가지

| 방법 | 하는 일 | 장점 | 주의점 |
|---|---|---|---|
| **class_weight** | 양성을 틀리면 더 큰 벌점 | 원본 데이터 그대로 사용 | 모든 모델에서 되는 건 아니고 확률 분포가 달라질 수 있음 |
| **undersampling** | 다수 클래스 일부 제거 | 학습 속도 빨라짐 | 중요한 다수 클래스 정보까지 삭제될 수 있음 |
| **SMOTE** | 소수 클래스 사이에 가상 데이터 생성(보간) | 단순 복제가 아닌 새 데이터 생성 | 경계·노이즈 근처에서 잘못된 가상 데이터 생성 가능 |

> "한 팀 사람이 너무 적으면, 혼내는 점수를 더 크게 하거나(class_weight), 다른 팀 사람을 조금 빼거나(undersampling), 같은 팀 친구들 사이에 새 친구를 만드는(SMOTE) 방법이다."

**SMOTE를 텍스트/One-hot에 쓰면 안 되는 이유**: SMOTE는 두 벡터의 중간값을 만드는데, One-hot은 0/1만 의미가 있어 중간값(0.3, 0.7)이 실존하지 않는 데이터가 된다. TF-IDF나 임베딩도 마찬가지로 두 문장 벡터의 중간이 실제 존재하는 문장이라는 보장이 없다("고양이가 귀엽다"와 "자동차가 달린다"의 중간이 "귀여운 자동차"를 의미하지 않음).

**SMOTE는 train에만 적용**해야 한다. validation/test에까지 적용하면 미래 데이터를 보고 가짜 데이터를 만드는 셈이라 성능이 실제보다 부풀려 보인다(시험문제를 미리 보고 공부한 것과 같음).

## 5. 교차검증 — 배포 후 새로 만날 단위에 맞춰 분할

같은 모델인데 분할 방법을 바꾸면 validation AP가 0.79 → 0.63처럼 크게 흔들릴 수 있다. **교차검증은 한 번의 분할 우연을 줄여주지만, 잘못된 분할 기준 자체를 고쳐주지는 않는다.**

먼저 "배포 후 새로 만날 것은 새 행인가, 새 문서·사용자인가, 미래 시점인가?"를 정해야 splitter가 결정된다.

* **StratifiedKFold**: 각 fold의 클래스 비율을 유지. 단, 같은 문서·사용자·대화에서 나온 행이 train/validation에 섞이는 것은 막지 못함.
* **GroupKFold**: 같은 group(문서·사용자·대화)이 train과 validation에 동시에 들어가지 않게 함.
* **StratifiedGroupKFold**: group 경계를 지키면서 클래스 비율도 최대한 유지. 단, 양성을 가진 그룹이 각 fold에 들어갈 만큼 충분히 많아야 함.

같은 원문에서 나온 chunk를 일반 KFold로 나누면 train/validation에 같은 문서가 섞여 **데이터 누수**가 생기고 성능이 과대평가된다.

**대표적 데이터 누수**: 데이터를 나누기(split) 전에 `fit()`을 하면 validation의 정보가 train으로 새어 들어간다.

**Pipeline**은 전처리와 모델을 하나로 묶어 CV가 매 fold마다 현재 fold의 train에서만 전처리를 학습하게 한다. 단, Pipeline이 막아주는 건 "fold 밖 fit" 뿐이며, **잘못된 분할 기준, 미래 특성 포함, test 반복 확인**은 막아주지 못한다.

**평가 절차를 고정하는 순서**:
1. "배포 후 새로 만날 단위와 예측 시점"을 한 문장으로 적는다 (예: "내일 들어오는 새 이메일을 예측한다") → 새 행이면 KFold, 새 개체면 Group 계열, 미래면 시간 분할.
2. 모든 학습형 전처리·리샘플링을 fold의 train 안에서만 수행.
3. fold 평균과 흔들림을 함께 보고, 유난히 낮은 fold의 원인(특정 고객/병원/시기)을 확인.
4. 모델·특성·threshold 선택은 개발 데이터(train+validation)에서 끝낸다.
5. 선택한 Pipeline을 개발 데이터 전체로 다시 fit하고, 봉인한 test에서 후보 하나를 한 번만 평가.

## 오늘의 핵심 정리

* 불균형 데이터에서는 Accuracy보다 먼저 **양성률과 TP·FP·FN·TN**을 확인한다.
* **Precision·Recall·F1**은 threshold 한 점의 성능, **ROC-AUC·AP**는 점수 순위 전체의 성능을 평가한다 — 대체 관계가 아니라 목적이 다르다.
* 희소 양성에서는 **ROC-AUC만으로 판단하지 말고 AP를 함께** 본다. AP와 사다리꼴 PR-AUC는 계산이 다르다.
* **class_weight(벌점) / undersampling(제거) / SMOTE(추가)**는 트레이드오프가 다르며, SMOTE는 One-hot·텍스트 임베딩에는 부적합하고 train에만 적용한다.
* **threshold는 모델이 아니라 운영 정책**이다. 오류 비용을 반영해 validation에서 정하고, 선택을 고정한 뒤 test는 봉인해서 한 번만 연다.
* 교차검증은 **가장 높은 점수를 주는 splitter가 아니라, 실제 배포 상황과 가장 닮은 splitter**(Stratified/Group/Time)를 골라야 의미가 있다.
* Pipeline은 fold 밖 fit(누수)을 막아주지만, 분할 기준 자체가 틀렸거나 test를 반복 확인하는 실수는 막아주지 못한다.
