# TIL | CV 기반 하이퍼파라미터 탐색과 누수 없는 End-to-End Pipeline

**2026-08-18**

하이퍼파라미터 후보를 고를 때도, 전처리·리샘플링·모델을 이어붙일 때도 원칙은 같다. **test를 보기 전에 규칙을 먼저 고정하고, 개발 데이터 안에서만 결정한다.** 오늘은 CV로 후보를 공정하게 선택하는 법(5장 1강)과, 그 선택을 재현 가능한 하나의 Pipeline으로 묶어 저장·재사용하는 법(5장 2강)을 다뤘다.

---

## 1. 파라미터 vs 하이퍼파라미터, 그리고 CV 후보 선정 규칙

모델이 데이터에서 직접 학습하는 값(가중치, 분할 기준)이 **파라미터**, 트리 수·최대 깊이처럼 학습 전에 사람이 정하는 값이 **하이퍼파라미터**다. 하이퍼파라미터 탐색은 여러 설정을 학습시켜 보고 일반화 가능성이 높은 후보를 고르는 과정이며, 각 후보는 같은 4-fold CV로 평가한다.

**결과를 보기 전에 먼저 고정해 둔 후보 선정 규칙**:

1. 전체 후보 중 가장 높은 CV 평균 AP를 찾는다.
2. 최고 평균과 AP 차이가 0.01 이내인 후보만 남긴다(`eligible`).
3. 남은 후보 중 fold 표준편차가 가장 작은 후보를 고른다.
4. 표준편차까지 같으면 트리 수 → 깊이 → 탐색법 이름 순서로 동률을 푼다.

test는 이 모든 선택이 끝난 뒤 **한 번만** 확인한다.

---

## 2. Grid Search와 Random Search — 같은 예산으로 비교

| | 방식 | 언제 유용한가 |
|---|---|---|
| **GridSearchCV** | 미리 정한 이산 조합을 빠짐없이 평가 | 공간이 작고 살펴볼 값이 분명할 때 |
| **RandomizedSearchCV** | 넓은 후보 목록·분포에서 `n_iter`개를 샘플링 | 정해진 후보 수 예산으로 다양한 좌표를 보고 싶을 때 |

두 탐색법을 공정하게 비교하려면 **탐색법당 같은 후보 평가 횟수**(오늘은 12개)로 맞춰야 한다. 참고로 이전 trial 결과를 학습해 다음 후보를 추론하는 방식은 **Bayesian Optimization**(Optuna의 TPE)이며, Grid/Random과 달리 완료된 결과를 참고해 다음 후보를 제안한다는 점이 다르다.

> Optuna의 pruning은 `trial.report(score, step)`으로 중간 성적을 계속 보고해야 동작한다. `RandomForestClassifier.fit()`처럼 한 번에 끝나는 학습은 중간 점수를 보고할 기회가 없어 **pruner를 설정만 해도 아무 효과가 없다.** 또한 pruning이 걸리면 trial마다 실제 학습량이 달라지므로, 완료된 trial 수·실제 fit 횟수·총 실행시간을 함께 기록해야 공정한 비교가 된다.

## 3. 결과 전에 규칙을 고정한다 — 후보 확정 절차

코드로 확인해야 할 부분:

* 두 `cv_results_`의 모든 행을 `candidate_rows`에 합친다.
* 최고 평균 AP에서 0.01 이내인 후보만 `eligible`로 남긴다.
* 남은 후보는 fold 표준편차가 작은 순서로 정렬한다.
* 표준편차까지 같으면 트리 수 → 깊이 → 탐색법 이름 순으로 동률을 푼다.
* 후보를 고르는 함수는 `fitted_searches`만 받는다 — **`X_test`, `y_test`는 입력에 없다.**

후보가 고정된 뒤에야 개발 데이터 전체로 다시 학습하고, 마지막에 봉인한 test를 연다.

### fold 표준편차를 해석할 때의 주의

`0.657 ± 0.055`의 `±0.055`는 각 CV fold에서 AP가 얼마나 들쭉날쭉했는지를 나타낼 뿐, test 성능 범위도 95% 신뢰구간도 아니다. 평균 AP가 0.50인 모델이 모든 fold에서 0.49~0.51이면 표준편차는 작지만 성능 자체는 낮다 — 그래서 **평균 AP가 높은 모델을 먼저 고르고, 비슷한 후보끼리만 표준편차를 비교한다.** `StratifiedKFold`는 fold별 클래스 비율을 맞춰주기 때문에 fold들이 실제보다 더 비슷해 보여 표준편차가 작게 나올 수 있다. 정말 중요한 평가라면 `RepeatedStratifiedKFold`, `GroupKFold`, `TimeSeriesSplit` 등으로도 확인한다.

> "모의고사 점수가 시험마다 얼마나 흔들렸는지 보는 것이 표준편차이고, 그게 작다고 꼭 공부를 잘한 것은 아니다." — 꾸준함(표준편차)보다 평균 실력(평균 AP)이 먼저다.

## 4. Pipeline으로 학습 순서를 고정한다

`ColumnTransformer`로 열별 전처리를 나누고, 전체를 하나의 Pipeline으로 묶는다.

| 입력 열 | 전처리 | 이유 |
|---|---|---|
| 수치형 3개 | median imputation → StandardScaler | 결측값을 채우고 단위 차이를 조정 |
| route(범주형) | most-frequent imputation → One-Hot Encoding | 문자 범주를 모델이 읽을 수 있는 열로 변환 |

```python
preprocessor = ColumnTransformer([
    ("num", numeric_pipeline, numeric_columns),
    ("cat", categorical_pipeline, categorical_columns),
])
```

합성 데이터를 만들 때 쓴 **베타(Beta) 분포**도 눈에 띄었다. 0~1 사이 값만 나오는 분포라 확률·비율·점수(독성 점수, 클릭 확률, 불량률 등)를 모델링하기 좋고, 정규분포와 달리 음수나 1 초과 값이 나오지 않는다. `α`가 크면 0에서 멀어지는 힘, `β`가 크면 1에서 멀어지는 힘이 커진다 — `rng.beta(1.5, 8.0, n)`처럼 β가 훨씬 크면 분포가 0 쪽으로 몰린다.

5-1의 CV 후보 선정 원칙(평균 AP 우선 → tolerance 내 std 비교 → tie-break)은 개별 하이퍼파라미터뿐 아니라 **Pipeline 설정 전체**를 고를 때도 그대로 적용한다.

## 5. Oversampling 이후의 확률은 "점수"로 해석

`predict_proba()`는 원래 클래스 확률을 반환하지만, `RandomOverSampler`로 소수 클래스를 복제해 학습하면 원본과 다른 클래스 비율로 학습된 것이라 출력값을 실제 발생 확률로 그대로 해석할 수 없다. 대신 `needs_review=1`일 가능성이 얼마나 큰지를 나타내는 **점수(score)**로 해석해 검토 우선순위를 매기는 용도로 쓰는 것이 적절하다. A>B>C>D 같은 상대적 순서는 여전히 믿을 만하다.

> 병원 응급실의 중증도 점수와 같다. "90% 확률로 위험하다"는 뜻이 아니라 **다른 환자보다 먼저 봐야 할 정도**가 높다는 뜻이다.

같은 맥락에서 threshold도 "위험도 30% 이상"이 아니라 **"업무 조건(예: Recall 80% 이상)을 만족시키는 기준선"**으로 해석해야 한다. 모델 선택과 threshold 선택도 같은 데이터로 하지 않는다 — `model_train`으로 모델을 고르고, 학습에 쓰지 않은 `threshold_validation`으로 threshold를 고른 뒤, 모두 고정된 후에 test를 한 번만 연다.

## 6. 모델 파일 하나로는 부족하다

Pipeline을 `joblib.dump`/`load`로 저장·재사용할 수 있지만, 실제 운영에는 모델 파일 이상이 필요하다.

* **모델**: `review_pipeline.joblib` — AI의 두뇌
* **결정 정책**: threshold 등 "몇 점 이상이면 검토 필요"인지의 규칙
* **입력 schema**: 필수 컬럼, 자료형, 결측 허용 여부 등의 약속
* **재현 정보**: Python·scikit-learn 버전, 데이터 버전
* **보안 정보**: 모델 파일 변조 여부를 확인하는 hash·서명

reload 전후 같은 입력의 점수는 허용 오차 안에서, 0/1 예측은 정확히 같은지 반드시 검증한 뒤 배포한다. API는 요청마다 Pipeline을 load하지 않고 서비스 시작 시 한 번만 load하며, 정답이 없는 동안은 결측률·새 범주·범위 이탈·점수 분포·검토율·지연시간을 모니터링하고 정답이 쌓이면 Recall·Precision을 확인한다. SHAP이나 회귀 계수는 모델이 어떤 입력에 반응했는지 보여줄 뿐 인과관계를 증명하지 않으며, 그 결과를 보고 같은 test에서 모델을 다시 고르지 않는다.

## 오늘의 핵심 정리

* 하이퍼파라미터 후보는 개발 데이터 안에서 같은 CV로 평가하고, **결과를 보기 전에** 선정 규칙(평균 AP → tolerance 내 std → tie-break)을 고정한다. test는 선택이 끝난 뒤 한 번만 연다.
* Grid Search와 Random Search는 **같은 후보 평가 횟수**로 비교해야 공정하며, Optuna pruning은 중간 점수를 보고할 수 있는 학습에서만 의미가 있다.
* fold 표준편차는 test 범위나 신뢰구간이 아니다 — 평균 AP가 비슷한 후보끼리만 비교 기준으로 쓴다.
* `ColumnTransformer` + imblearn Pipeline은 전처리·리샘플링·분류 모델의 학습 순서를 하나로 고정하며, sampler는 fold train과 최종 refit에서만 실행되고 validation·test·새 요청 예측에는 실행되지 않는다.
* Oversampling 이후의 `predict_proba()`는 확률이 아니라 **순위 점수**로 해석하고, threshold는 모델의 일부가 아니라 **운영 정책**이다.
* 배포에는 모델 파일뿐 아니라 **결정 정책 + 입력 schema + 재현 정보 + 보안 정보**가 함께 필요하며, reload 전후 결과가 같은지 검증한 뒤 배포한다.
